一、这一轮要的是什么

需求原话

「拉黑插件的悬浮窗不能被拖出页面以外，悬浮窗的边界就是用户的页面边界。」

我先没动手，把现状和四个决策点摆出来让你拍板。四个决定一共省掉的返工，比讨论花掉的 15 分钟值钱。

决策点你选的它意味着什么
① 钳哪些元素A 球 + 面板两者共用同一个拖动函数，改一处都受管
② 贴边口径B 沿用 4px 内缩与初始摆放、自愈同一套钳制，不会出现"拖着贴边、一 resize 又弹开 4px"
③ 撞边手感A 撞边即停往外拖多远、往回拖就要走完那段空程（已知代价；换 B 约 5 分钟）
④ 元素比视口大A 只锁边不做自适应；视口窄于 338px 时面板右侧会被裁
越位处置暴力拉回默认位置只要有任一边探出视口，球直接回右下角，不做"钳到最近边界"

二、把这件事拆成四层看（点开每一层）

第一层 · 拖动层 makeDraggable谁在动

职责：把手指/鼠标的位移换成元素的新位置；判断这次手势到底算"拖动"还是"点击"。

  • 用 pointer 事件 + setPointerCapture：手指滑出元素后仍收得到 move
  • touch-action:none：拖动时页面不跟着滚
  • 阈值 DRAG_MIN=5：位移不到 5px 算点击，否则算拖动（这一版才统一）

这一层最容易出的错：指针事件与"触屏兼容鼠标事件"各触发一遍 → 一次点按翻两下；两个阈值不一致 → 中间地带既挪又开。

第二层 · 钳制函数 clampToViewport能到哪

职责：把目标坐标夹进"视口减元素尺寸再留 4px"的范围内。整个边界需求就落在这一个函数上。

function clampToViewport(left, top, w, h) {
  var vw = window.innerWidth || 0, vh = window.innerHeight || 0;
  var maxL = Math.max(4, vw - (w || FAB_SIZE) - 4),
      maxT = Math.max(4, vh - (h || FAB_SIZE) - 4);
  return { left: …, top: … };
}

注意 Math.max(4, …)：当元素比视口还大（vw - w - 4 < 4）时上界退化成 4 → 只能锁在左/上边，右侧溢出无法避免。这就是你选的 ④A 在代码里的样子。

第三层 · 自愈层 keepInView被挤到之后

职责：视口变了（转屏、键盘弹出、地址栏收放）之后，把越界的东西拉回来。

  • 触发点：resize、orientationchange、构建后 1.5 秒兜一次、以及新增的 ResizeObserver（面板自己长高不发 resize 事件）
  • 球的处置按你的口径：任一边探出视口 → 直接回默认右下角（不做"钳到最近边界"的温柔处理）
  • 面板的处置保留钳回：面板 330px 宽，窄视口下"回默认摆放"本身也放不下
第四层 · 发布链 loader → CDN 边缘 → 主脚本你拿到的是哪版

这一层不在插件代码里，但它决定"你屏幕上跑的是哪一版"，本轮真正花时间的地方。

  • loader v2.0 的活法：把所有候选地址**并行取回文本**（不执行）→ 从每个文件里读出 const VERSION = 'x.y.z' → 取最高的那份注入
  • 候选来源：同主机 @main、无 ref 地址（= 最新 tag 快照）、GitHub API 给的最新 tag 拼出的**不可变**地址、以及 fastly / gcore 两个备用域名上的同样组合
  • 为什么非要这么绕：jsdelivr 对**分支引用**的缓存是 12 小时，?t=时间戳 只能绕浏览器、绕不掉 CDN；不同边缘节点回源节奏不同 → 同一时刻 @main 在各主机上是**不同版本**

五、排查台阶：你屏幕上跑的到底是哪一版

顺序不能乱。三层判完，故障属于哪一类就锁定了 —— 这是本轮从"猜一版发一版"里学到的。

第 1 层 · 看界面上的版本号

插件在面板标题上永远印着版本（🚫 拉黑屏蔽 vX.Y.Z），悬浮球 title 也有。这是**实际运行的版本**，不是"我以为发布了"的版本。你说"还是老样子"时，第一句要问的就是它。

第 2 层 · 看 loader 有没有留下状态对象

v2.0 的 loader 会把探测结果写进 window.__IIROSE_BLACKLIST_LOADER__（选了哪个地址、每个候选各是什么版本）。

JSON.stringify(window.__IIROSE_BLACKLIST_LOADER__ || 'no-loader-state')

返回 no-loader-state = 跑的**不是** v2.0 loader（旧 loader 或 extJs 里另有一份老地址）；返回带 chosen/probes 的对象 = v2.0 在岗，直接看它列的版本。

第 3 层 · 逐个地址实测 CDN 给的是哪版 
curl -s "https://cdn.jsdelivr.net/gh/<owner>/<repo>@main/<file>.js" | grep -o "VERSION = '[0-9.]*'"

本轮实测（同一时刻）：
cf @main → 0.3.8 ／ fastly @main → 0.3.10 ／ 无 ref → 0.3.10 ／ tag 快照 → 0.3.10
同一仓库、同一时刻，两台主机给出两个版本 —— 这就是横跳的全部原料。

结论：要稳定，就把地址**钉到 tag**（不可变、CDN 上第一次请求必然回源），或者用一个会自己比版本的 loader。

六、变异检验：全绿不等于有用

这轮唯一比前几版强的地方。夹具全绿只说明"现在的实现能过"，不说明"测试抓得住回归"。做法：故意把实现改坏（退回旧行为），看夹具会不会红。点下面两个开关，看它变红还是照旧绿。

两次都红了。第一次实测：局部越位后旧版把球钳到 (4,120)，新版落默认位置 (1202,364) —— 夹具第 7 组当场 FAIL。第二次：点「关闭」窗口不消失 —— 第 10 组 FAIL。

七、五个坑（现象 → 根因 → 能带走的）

坑 1 · 诊断大字窗口关不掉

现象：窗口里的「关闭 / 复制全文 / 刷新」全都点不动。根因：窗口在捕获阶段对 pointerdown/click/… 调了 stopPropagation —— 捕获阶段是从外往里走，一停，事件根本到不了自己的后代按钮。
带走的：想"拦截事件别往外冒"就写在冒泡阶段；捕获阶段的 stopPropagation 是把自己后代一起关在门外。

坑 2 · 夹具的断言句句 FAIL，插件其实是对的

现象：找不到面板元素、或拿到一个宽高为 0 的东西。根因：夹具脚本源码里写着 /拉黑屏蔽 v/ 这类字面量，而 document.body.children 里那个 <script> 的 textContent 就是源码 → 按文本找元素时匹配到了夹具自己。
带走的：按 textContent 找元素必须加 tagName 过滤；夹具一开跑就先挂 window.onerror 把异常写进结果区，否则页面永远停在"跑测试中…"，你会去翻插件代码而真因在夹具。

坑 3 · 位移 4px 时，球既挪了又开了面板

现象：手指轻抖一下，球位置变了、面板也弹出来。根因：拖动判定 moved > 3、点击判定 moved < 5 —— 中间那 1px 地带两边都算，两个动作都发生。
带走的：同一件事的两个阈值必须合一（DRAG_MIN），别留缝。

坑 4 · 面板贴底以后自己长高，底部按钮够不着

现象：新消息进名单 → 面板长高 → 底部探出屏幕，而且不会自己回来。根因：尺寸只在按下时量了一次；自愈只挂在 resize 上，而"面板自己长高"不发 resize 事件。
带走的：会变的尺寸每帧现量；落盘前再钳一次；尺寸变化用 ResizeObserver 补一条触发路径。

坑 5 · git 推不上去，报 schannel 握手失败

现象：fatal: … schannel: failed to receive handshake，但同一台机器 curl 走同一个代理访问 github 是 200。根因：Windows 自带的 schannel TLS 后端对 github 握手失败（本机老毛病）。
带走的：换后端 git config --global http.sslBackend openssl，一次设好。
