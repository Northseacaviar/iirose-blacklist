## 三、逐条回答你点名的 8 个问题

### (a) 坐标系 vdx/vdy 自洽吗？offsetParent / 页面滚动会算错或第一帧跳吗？

**自洽，且在插件的真实装配下 vdx/vdy 恒为 0。**

实测（Chromium，把 `position:fixed` 元素挂在 `document.body`）：

| 情形 | `rect.left − offsetLeft` | `offsetParent` |
|---|---|---|
| 普通（body margin 0） | 0 | `null` |
| body `margin:30px` | 0 | `null` |
| 页面滚动 500px | 0 | `null` |
| 祖先带 `transform:translate(33px,44px)` | **33**（`offsetTop` 差 3771） | 该 DIV |

`position:fixed` 且 `offsetParent === null` 时，`offsetLeft` 就是相对视口的值，与 `rect.left` 相等——所以插件把 `fab`/`panel` `appendChild` 到 `document.body`（src:1593-1594）时 `vdx = r0.left − ox = 0`。夹具自己那行诊断也打印 `坐标差 rect.left−offsetLeft = 0.00 / 0.00`。body 的 margin、页面滚动都不影响它。

**第一帧不跳**：实测按在球心（500,300），位移 4/10/10/25px 依次读位置 = `504, 510, 510, 525`，逐像素精确跟随，没有跳变。

**唯一能造出 vdx ≠ 0 的世界**：祖先（含 body/html）带 `transform`/`filter`/`perspective` 时，fixed 元素的包含块会变成那个祖先，`offsetParent` 不再是 null，`vdx/vdy` 变成非零。这时补偿公式 `clamp(ox+dx+vdx) − vdx` **方向是对的**（实测：body 加 `translate(40px,60px)` 后把球拖到左上角，rect 精确落在 (4,4)，style 存 −36,−56）。但同一份假设在别的路径上没跟着补——见建议 **S4**。另外注意 `vdy` 在这种世界里会随页面滚动变化（实测祖先 transform + 页面滚 300px，`rect.top − offsetTop` 从 3771 → 3471），补偿只在「一次手势内不滚动」时成立。

### (b) ew/eh 只在 start 量一次、整个手势复用，对不对？拖动中途视口变化会怎样？

**这一条是本轮最实的问题，见中等项 M2。** 结论：

- 「量一次」在**面板高度被 `maxHeight` 封顶**（src:1303，面板自身 `overflowY:auto`）时影响有限；但面板**没有顶到 maxHeight** 时，高度是会变的，而且真机上有真实触发路径：新消息 → `hookCbs.onSeen` → `ui.refreshSeen()`（**src:637-643**）→ 重建「最近出现」名单 → 面板变高。
- **实测（拖动中途尺寸变大）**：手势按下时面板高 200px（`maxHeight:200px`），在 `pointerdown` 与 `pointermove` 之间把 `maxHeight` 放回 540px（等价于名单/日志变长 340px），向下拖出视口 → 面板 `top=420, bottom=960`，视口高 624 → **底部探出视口 336px**，而且**之后没有任何自愈**（`keepInView` 只在 resize/orientationchange/加载后 1500ms 跑）。
- **拖动之后尺寸变大也一样**：面板停在视口底部后每多一行「最近出现」就往下长一点，`keepInView` 不会因为内容变化被调用，多出来的部分就留在视口外（做 4px 级实测：`maxHeight` 由 520→560 时底部立刻探出 36px，无 resize 就一直探着）。
- **拖动中途视口变化**：`keepInView` 会被 resize 触发。若此时球被判越位，会被重置一次到默认位；紧接着下一次 `pointermove` 又把它拉回手指下面（有一帧拉扯感，但位置不会算错）。面板在拖动中途被 resize 钳一次、后续 move 又按 `ox+dx` 覆盖回钳后的位置，结果一致，无累积错位。

### (c) moved > 3 才动、moved < 5 算点击：贴着边界点一下球（位移 0）会不会被误判？

**不会。** 位移 0 → `moved = 0` → 走 `moved < 5` → `onClick()`（src:1257-1262）。实测：把球拖到左上角 (4,4) 后 `pointerdown`+`pointerup` 同坐标 → 面板 `display: none → flex` 正常开合并合。夹具 [2] 也覆盖了这条（它是活的：把 `moved < 5` 改成 `moved < 0` 后夹具 15/3，见 M6）。

**但中间地带 `3 < moved < 5` 两种行为会同时发生**：实测 4px 抖动 → 球从 (4,4) 挪到 (8,4) **并且**面板被打开。这不是本轮引入的（阈值本来就是 3/5），但既然这次把「贴边」当成一条口径，顺手统一更省事——见建议 **S6**。

### (d) clamp 返回整数减去可能带小数的 vdx 再 Math.round：会 1px 抖动或累积误差吗？

**不会抖、不会累积。** 原因是写回用的是**绝对基准**而不是增量：每帧都从 `ox + dx`（手势起点 + 累计位移）重算，`Math.round` 的单帧量化误差不会带到下一帧。实测：

- 撞到左边界后继续往外推 40 次（每次 −5px）→ 位置**恒为 4**，一次没抖。
- 连续 6 次「拖到左上角外」→ 每次落点都是精确 `4,4`。
- `vdx` 为小数时（祖先 transform 那种世界）单帧误差 ≤ 0.5px，且不跨帧累积；`ew/eh` 即使带小数（实测面板高 592.2），`clampToViewport` 的 `maxL/maxT` 带小数也没关系，最终 `left/top` 一定被 `Math.round` 收成整数 → `style.left` 恒为整数值。

### (e) 「任一边越界就回默认」容忍 1px：地址栏收放会让球频繁跳回右下角吗？贴边球 `right == vw−4` 会被误判吗？

**两个答案相反：**

- **贴边不会误判** ✓。球钳到 `right = vw−4`，判据是 `r.right > vw + 1`（src:1608-1609），不成立 → 不越位。实测：球贴右下 (1212,574) 后派发一次同尺寸 resize，位置**一格没动**。垂直方向同理（`bottom = vh−4`）。
- **地址栏确实会把它踢回默认** ✗（这是口径的必然结果，不是代码 bug，但频率高）。实测：球贴右下 (1212,574) @ 视口 1262×624 → 视口高度缩 60px（等价地址栏出现）→ 球落到 **(1202, 304)** = `defaultFabPos()` 的 `vw−60 / vh−260`；视口还原成 624 后球**不会回到 (1212,574)**，就停在 (1202,304)。也就是说用户每遇到一次地址栏出现，自己摆好的球就往页面中部跳约 270px，且不可逆。因为你点在 (e) 里问了，我把它列成中等项 **M3**（改法一行三元表达式）。

### (f) 面板保留钳回、球改成回默认，两者不一致有实际隐患吗？

**在「插件挂在 document.body、无 transform」的现实世界里：没有功能性隐患。** 面板是钳回，只会越钳越靠内；两者的差别只体现在「用户摆好的位置会不会被重置」这一个产品手感上（面板不丢位置、球丢）——这是你点名的刻意口径。视觉上可能出现一次「球被拉回默认、正好压在面板上/面板被钳回到球底下」，纯视觉，点得到。

**真正的隐患在 `vdx ≠ 0` 的世界里**：`drag` 路径减了 `vdx/vdy`，而 `keepInView` 的面板分支（src:1618-1623）、`setPanelPos`（src:1634-1640）、`placePanel` 用的 `saved`（src:1647）全都按「rect 坐标 == style 坐标」处理。实测（body 加 `transform:translate(40px,60px)`，`vdx=40 / vdy=60`）：

- 面板拖到右下 → 落盘 `{left:888, top:20}`（style 坐标），下次打开时 `setPanelPos` 把它当视口坐标用 → 差 40/60px；
- `keepInView` 把 `clampToViewport` 的结果（视口坐标）直接写进 style → 面板 rect 落在 **(44,64)**，而意图是 (4,4)；
- 球被拉回默认后 style=1202/364 → rect.right = **1288 > vw 1262**，**球探出视口右侧 26px**（违背本轮验收标准，且要等下次拖动才纠正）。

前提是站点给 body/html 加了 transform（GPU 合成的 `translateZ(0)`、动画都常见）——**这条前提我没能在真机上验证**（站点需登录）。按「低概率但代价明确的非对称风险」处理，列建议 **S4**。

### (g) 夹具的断言有没有假绿风险？合成 PointerEvent 下 pointer capture 被 try/catch 吞掉会不会让夹具和真机不一致？

**夹具整体是「活」的，但有一个正好踩在本次核心改动上的盲区。**

变异测试（每组只改一处，跑在副本目录，7 组）：

| 变异 | 改坏什么 | 改前 → 改后 | 捕获 |
|---|---|---|---|
| M1 | `move()` 里的 `clampToViewport` 整个去掉 | 18/0 → **5 通过 / 13 失败** | ✓ |
| M2 | 球越位**判据**退回旧版（只改判据） | 18/0 → **18 通过 / 0 失败** | ✗ |
| M3 | 拖动彻底不动（`style` 永不写） | 18/0 → **14 / 4** | ✓ |
| M4 | 球越位改成「钳回」而不是「回默认」 | 18/0 → **16 / 2** | ✓ |
| M5 | 贴边内缩 4px → 60px | 18/0 → **15 / 3** | ✓ |
| M6 | 点击路径失效（`moved < 0`） | 18/0 → **15 / 3** | ✓ |
| M7 | **球分支整段退回 v0.3.7**（旧判据 + 旧 `clampToViewport` 兜底） | 18/0 → **18 通过 / 0 失败** | ✗ |

- **假绿的「没拖成」风险已被夹具自己防住**：M3（拖动不生效）触发了 4 条失败，其中就包括 [6] 那条专门的对照断言（`拖动确实发生了且没有越界（不是"没动"造成的假绿）`，夹具 161-166 行）。这一条是有效的。
- **真正的盲区（中等项 M1）**：夹具 [5] 用 `fab.style.left = '-800px'`（**完全出界**）造越位。而「完全出界」在新旧两套判据下**结果相同**（都会回默认），新判据真正新增的能力是**局部越位**（任一边探出 1px 以上、但还没完全出界）也回默认。夹具没有任何局部越位的输入 → M2/M7 全绿。实测行为差异：球放 `left=-30px` 后 resize，v0.3.8 落到默认 **(1202,364)**，v0.3.7 语义落到 **(4,120)**——夹具分辨不出来。
- **pointer capture**：实测合成事件下 `setPointerCapture(1)` **没有抛异常**（Chromium 里返回成功），但 `hasPointerCapture(1) === false`——**捕获根本没建立**。也就是说夹具跑的是「事件直接派发到元素上」这条路，真机的「手指/鼠标滑出元素后仍持续收到 move（真捕获或触屏隐式捕获）」没被覆盖。夹具这样写仍能驱动插件（插件的 `move` 挂在 handle 上，且真机即使捕获失败还有 `document` 的 mousemove 兜底、触屏有隐式捕获），所以**不会掩盖本轮的问题**，但它确实测不到捕获相关回归——见建议 **S3**。
- 另外夹具是**按桌面视口写死**的，在窄视口会大量假 FAIL：实测 330×560 视口下 **9 通过 / 9 失败**（面板宽 330 正好等于视口宽，`right=334 > vw`；且球越位那条期望值用的是宽屏公式 `vh−260`）——见建议 **S1 / S2**。

### (h) 有没有遗漏的边界情形？

已实测、**结论正常**的：

- **pointercancel 中断**：只 `dragging = false`（src:1265），不结算。实测取消后元素停在被钳住的位置，随后补一个 `pointerup` 不会重复结算，**之后还能正常点击开面板、能重新拖**。状态干净。
- **多次 resize 叠加**：`keepInView` 幂等（只比 `left/top` 有没有变），连打几次无副作用。
- **拖动结束那一帧尺寸变化**：`end()` 存的是 `node.offsetLeft/Top`（src:1261 → 1675-1679）。就算存下来时已越界，下次开面板 `placePanel` → `setPanelPos`（src:1634-1640）会再钳一次 → **能自愈**。
- **面板隐藏时被拖动**：`display:none` 收不到指针事件，不可达。Esc 在拖动中途把面板关掉这种极端情形下，`dragging` 会留在 true，但 `start()` 每次都会重置，无残留；
- **拖到边缘后继续外推**：位置锁死、不抖（见 (d)）；回拖的「空程」实测 **220px**（从 200 拖到左墙后再往回 220px 才开始动），与你选的方案 A 一致，不报。

**漏掉的（= 中等项 M2 的两种触发路径）**：尺寸在「拖动中途」和「拖动之后」变化，都不会被重新钳，面板可以长期真的停在视口外。

**M2 —— 元素尺寸在拖动中途/拖动之后变化时不复钳，面板可以真的停在视口外**
- 文件/行号：`src/iirose-blacklist.js:1240-1241`（尺寸只在 `start` 量一次）、`1252`（整个手势用旧尺寸钳）、`1257-1262`（`end()` 结算时不再钳）、`1675-1679`（面板落盘直接用 `offsetLeft/Top`）、`1602-1626` + `1628-1630`（`keepInView` 只在 resize / orientationchange / 加载后 1500ms 跑，内容变化不触发）。真实触发源：`src:637-643`（新消息 → `ui.refreshSeen()` → 面板变高）。
- 为什么：`clampToViewport(ox+dx+vdx, oy+dy+vdy, ew, eh)` 里的 `eh` 是手势开始那一刻的高度。若元素在 `pointerdown` 之后变高，钳制仍然把它当成旧高度 → 顶部按旧高度钳住、底部按新高度伸出去。实测：手势中途高度 200→540px，面板落在 `top=420 / bottom=960`（视口高 624），**底部探出 336px**，并且没有任何后续自愈（除非用户再触发一次 resize/orientationchange）。拖动之后同理：面板停在视口底部、内容再长高时（`refreshSeen` 加一行约 30px，只要还没顶到 `maxHeight`）底部就再往下探一点，**没有 resize 就一直是探着**（实测：`maxHeight` 由 520→560 时面板底部立刻探出 36px 且不复位；顶到 `maxHeight` 之后增长被内部滚动吸收，不再变高）。这直接违背本轮验收标准里「面板在任意拖动后、以及 resize/orientationchange 之后，四边都在视口内」。
- 建议改法（最小改动，两处）：
  1. `move()` 里现量尺寸，别用手势开始的缓存：
     ```js
     const rNow = node.getBoundingClientRect();
     const p = clampToViewport(ox + dx + vdx, oy + dy + vdy, rNow.width || ew, rNow.height || eh);
     ```
     （`ew/eh` 保留作 `start` 时的兜底即可。）
  2. `end()` 里结算前再钳一次，并把 `keepInView` 提成同作用域的具名函数，落盘前调一次：
     ```js
     const end = () => { ... dragging = false;
       const q = clampToViewport(node.getBoundingClientRect().left, node.getBoundingClientRect().top,
                                 node.offsetWidth, node.offsetHeight);
       node.style.left = q.left + 'px'; node.style.top = q.top + 'px';
       ... };
     ```
     更稳的做法：给 `fab`/`panel` 各挂一个 `ResizeObserver(() => keepInView())`（面板列表变长也会自愈），注意别把 `keepInView` 里的写回再触发一次 RO 造成循环（写回后尺寸不变即可，RO 只在尺寸变时回调，安全）。

**M3 —— 移动端地址栏收放会把贴边的球整块拉回默认（离原位置约 270px，且不可逆）**
- 文件/行号：`src/iirose-blacklist.js:1608-1609`（判据）、`1628-1630`（`resize` / `orientationchange` 触发）。
- 为什么：这是你定的口径（任一边探出 → 回默认）的**直接后果**，不是 bug；但触发频率高——移动端地址栏每出现一次视口就矮几十像素，只要球贴在（或靠近）下边，就被判越位。实测：球贴右下 (1212,574) @1262×624 → 视口高缩到 564 → 球落到 (1202,304)；视口还原后**不会回到 (1212,574)**。用户感知为「我自己摆好的球又跑到中间去了」。
- 建议改法（都是小改，你挑一个口径就能定）：
  a) 把「越位」分成两类——真出界（完全在视口外 / 尺寸为 0）→ `defaultFabPos()`；被视口缩小挤到（还有大半在视口内）→ `clampToViewport(r.left, r.top, r.width, r.height)`：
     ```js
     const gone = !r.width || !r.height || r.right <= 0 || r.bottom <= 0 || r.left >= vw || r.top >= vh;
     const out  = r.left < -1 || r.top < -1 || r.right > vw + 1 || r.bottom > vh + 1;
     const p = gone ? defaultFabPos() : (out ? clampToViewport(r.left, r.top, r.width, r.height)
                                             : { left: Math.round(r.left), top: Math.round(r.top) });
     ```
  b) 球分支干脆也改成「钳回」（与面板一致），把「暴力拉回默认」只留给完全出界——一行三元表达式的事，同时把 (f) 的不一致也消掉。
  c) 保持现状，但把「地址栏出现导致球回默认」写进 README 的已知取舍（至少别让真机验收时当成 bug 反复查）。

### 建议

**S1 —— 夹具 `def` 期望值只建模了 `defaultFabPos()` 的宽屏分支**
- `tests/drag-clamp.html:157`：`top: Math.min(Math.max(4, vh - 260), ...)` 写死了 `vh−260`，而 `defaultFabPos()`（`src:1283-1289`）在 `vw < 520` 时走另一支：`left = vw − FAB_SIZE − 8`、`top = vh − 108`（`FAB_SIZE` 还是加载时按 `innerWidth < 520` 定的 52）。
- 为什么：窄视口下这条断言必假 FAIL。实测 330×560 下报 `球越位 + resize → 回默认位置 [实测 270,452 期望 270,300]`——插件其实是对的。
- 改法：把期望值改成一个与插件同源的小函数（照抄 `defaultFabPos` 的分支），或让排障 API 暴露 `defaultFabPos()` 供夹具直接调用比对。

**S2 —— 夹具按桌面视口写死，窄视口下大面积假 FAIL**
- `tests/drag-clamp.html` 整体：假设了「视口比面板宽 8px 以上」（109 行的 `expMaxL/expMaxT`、115、132、138 行的 `vw − PW − 4`）与「4px 内缩能同时满足左右」。
- 为什么：面板固定 330px 宽 + 两侧 4px 内缩 → 视口 < 338px 时面板**必然**探出（这是你点名的已知取舍），但夹具把它报成 FAIL。实测 330×560：**9 通过 / 9 失败**，全是这类。
- 改法：夹具开头加一道闸——`if (window.innerWidth < 400) { 只跑球用例 + 输出「视口过窄，面板用例跳过」 }`；或把面板用例的期望值改成「`left === 4` 或 `left === vw - PW - 4` 中可用的那个」。

**S3 —— 合成事件下 pointer capture 实际不生效，真机那条路没被覆盖**
- `tests/drag-clamp.html:45-59`（`pev`/`dragTo` 把 `pointermove`/`pointerup` 直接派发到元素上）。
- 为什么：实测 `setPointerCapture(1)` 没抛（被 `src:1243` 的 try/catch 兜住也不会报），但 `hasPointerCapture(1) === false`，捕获根本没建立；夹具因此测的是「事件落在元素上」这条，而不是真机的「滑出元素后仍持续收到 move」。本轮改动不依赖捕获，所以**不掩盖本轮问题**，但它是一条测不到的回归通道。
- 改法：补一条——把 `pointermove` 派发到 `document`（模拟真捕获/触屏隐式捕获那条路），断言位置继续跟随；再补一条 `pointercancel` 中途打断后仍可继续拖动。

**S4 —— 坐标系补偿只在拖动路径上有；resize 自愈/摆放路径没跟着补**
- `src/iirose-blacklist.js:1242`（drag 减 `vdx`）vs `1610`（球非越位分支直接写 `round(r.left)`）、`1618-1623`（面板分支直接写 `clampToViewport` 结果）、`1634-1640`（`setPanelPos` 按视口坐标解释入参）、`1647`（`saved` 来自 `onDrop(node.offsetLeft, node.offsetTop)`，是 style 坐标）。
- 为什么：这些路径都假设「`rect` 坐标 == `style` 坐标」。当祖先（含 body/html）带 transform 时该假设不成立（实测 `vdx=40 / vdy=60`），后果：落盘的面板位置差 40/60px；`keepInView` 写了 style 但 rect 落在 (44,64) 而不是 (4,4)；球被拉回默认后 `rect.right = 1288 > vw 1262`——**探出视口 26px**（违背本轮验收标准）。前提未在真机验证（站点是否给 body/html 加 transform 未知）。
- 改法（任一）：① 在 `keepInView` 里现算差值并统一减掉（`const dx = fab.getBoundingClientRect().left - fab.offsetLeft;`，面板同理），让所有写回都走同一个换算；② 把 `fab`/`panel` 挂到一个自建的 `position:fixed; left:0; top:0` 容器里（`offsetParent` 恒为 null，`vdx` 恒为 0），从此不需要补偿；③ 至少在 `init` 里检测 `node.offsetParent !== null` 时记一条自检警告，真机排障时能立刻看见。

**S5 —— 面板 `maxHeight` 只在构建时按当时的视口高度算一次**
- `src/iirose-blacklist.js:1303`：`maxHeight: Math.min(540, Math.max(200, window.innerHeight - 40)) + 'px'`。
- 为什么：转屏/键盘把视口压矮后 `maxHeight` 还是 540 → 面板比视口还高，钳制只能锁到 4px（口径内的取舍），代价是面板底部的按钮滚不到、够不着。
- 改法：`keepInView` 里顺手重算一次（一行）：
  ```js
  panel.style.maxHeight = Math.min(540, Math.max(200, window.innerHeight - 40)) + 'px';
  ```

**S6 —— 移动/点击阈值的中间地带两种行为同时发生**
- `src/iirose-blacklist.js:1250`（`moved > 3` 才动）与 `1260`（`moved < 5` 算点击）。
- 为什么：`3 < moved < 5` 时**既移动又当点击**。实测 4px 抖动：球从 (4,4) 挪到 (8,4)，同时面板被打开。既有设计，非本轮引入。
- 改法：把两个阈值并成一个（例如 `const DRAG_SLOP = 5; if (moved > DRAG_SLOP) {...}` / `if (moved <= DRAG_SLOP) onClick()`），消掉中间地带。

**S7 —— `pointercancel` 只清 `dragging`，不更新 `ended`、不结算**
- `src/iirose-blacklist.js:1265`。
- 为什么：实测行为正常（取消后状态干净、可继续拖/点），但 `ended` 仍是上一个手势的 `gid`。当前无害（`end()` 头一行有 `!dragging` 早退），将来若有人在 `pointercancel` 里补「结算/落盘」逻辑，容易踩到「同一手势的 `mouseup` 又来一次」这个坑。
- 改法：`handle.addEventListener('pointercancel', () => { dragging = false; ended = gid; });` 并加一行注释说明为什么取消不结算。

**S8 —— README 的 A10 行格式与措辞**
- `README.md:49`：A10 那一行**后面缺空行**（紧接着就是 `## 协议与实现路线`），而同表其它行后都有空行；另外措辞「任意方向拖到视口外，都停在视口边界内」在视口宽 < 338px 时不成立（面板 330px + 4px 内缩）。
- 为什么：缺空行有渲染器把表吞进下一段的风险；措辞过强会让真机验收在窄屏/手机上误判成 bug。
- 改法：A10 行后补一个空行；措辞补一句已知取舍（「视口宽 < 338px 时面板必然探出约 4px；元素比视口高时只锁到 4px」）。
