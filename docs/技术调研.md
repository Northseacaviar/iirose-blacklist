## 二、核心结论：在收包层丢帧，而不是事后删 DOM

iiroseForge 的 `src/protocol/protocol.js` 里，房间消息与私聊消息的处理函数末尾都有：

```js
if (messageNeedBlock(senderId, content, senderName))
    return undefined;     // 该记录不写回包数据 → 客户端根本收不到
```

挂载点在 `src/injectIframe/initInjectIframe.js`：包装 `window.socket._onmessage`（站点自己的收包回调）：

```js
iframeContext.socket._onmessage = proxyFunction(
    iframeContext.socket._onmessage.bind(iframeContext.socket), (param) => { ... });
```

`param[0]` 就是解码后的帧字符串（gzip 已由站点自己解）。这是关键前提：**不需要自己接 WebSocket、不需要处理压缩**。

好处（相对"事后删 DOM"）：消息不进客户端 → 不渲染、不计未读、不响提示音、不闪一下；速度快且不依赖 DOM 结构。

 0 用户名  1 内容  2 颜色  3 颜色   4 5 头像     6 消息id     7 uid        8 头衔

其他帧（快照 `%`、心跳 `c`、媒体事件 `&1{...}`、弹幕发送 `~{...}`、协议回包 `` `~1 ``）一律**原样透传**——
这是"零影响"红线的实现方式：只认这三个前缀，认不出就不动。

## 四、DOM 兜底的必要性与选择器（依据 iiroseForge 源码）

为什么还要 DOM 兜底：拉黑**之前**已经渲染的历史消息不会自己消失；`%` 快照包里的历史消息也不走上面那三个前缀。forge 的 `enableBlacklist()` 给出了站点真实结构：

- 聊天消息容器：`document.getElementsByClassName("msgholderBox")[0]`
- 普通消息行：容器子节点中 `class="msg"`，`dataset.id = "uid_消息id"` → uid 取 `split("_")[0]`
- 头像：`.msgavatar`，带 `dataset.uid`
- 系统消息：`class="pubMsgSystem"`，其内层 `dataset.uid` 才是 uid（结构与 `.msg` 不同，要单独处理）
- 消息时间戳行：`class="pubMsgTime"`
- 私聊会话项：元素带 `ip="<uid>"` 属性（forge 的 `src/feature/uiHook.js` 用它取 uid 来做会话菜单）

本项目的 DOM 层据此实现，并额外处理了 forge 没覆盖的两点：
1. `dataset.id` 切分出来的不是 uid（uid 形态变了）时，回落用后代 `[data-uid]`；
2. 系统消息按"行"整体删除（向上找到 msgholderBox 的直接子节点），不留半截。

## 五、其他被验证的细节（都写进代码注释了）

- 注入方式：站点把地址存 `localStorage.extJs` → 每次页面加载往 iframe 注入 `<script src>`；脚本运行在 iframe 里，可直接访问 `window.socket` / `window.Objs` / `window.uid`（自己的 uid，用于"不能拉黑自己"）。
- `window.uid` = 当前登录用户唯一标识（forge `getUserUid()` 就是这么取的）。
- `window.socket` 只有在登录后才存在（`_onmessage`/`_send` 也是站点后挂的），所以要轮询等待后挂载。
- 站点「自定义 JS」的黑名单只管 `.imoe.xyz`，`http://127.0.0.1:<port>` 与普通公网地址都能注入。
